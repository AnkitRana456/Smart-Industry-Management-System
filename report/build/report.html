Abstract

Small and medium industrial units often run their machines, workers, production orders and stock on registers, spreadsheets and disconnected tools. A delay recorded in one place is invisible in another, maintenance is reactive, and managers cannot see the state of the whole floor without walking it. The Smart Industrial Management System (SIMS) is a web-based platform that brings these four areas into one real-time application with role-based access for administrators, managers and workers.

SIMS is built as a React and TypeScript client, a Node.js and Express REST API with Socket.io for live updates, MongoDB for storage, and a separate Python FastAPI service for machine learning. Machine status changes write downtime logs and raise alerts; production orders follow a validated state machine and consume materials atomically; stock movements are guarded so quantities never go negative and low stock drafts a purchase order that only a manager can approve. A dashboard and analytics pages present downtime, output, stock, attendance, reliability and OEE figures calculated by the backend.

The intelligence layer has two parts. A machine-learning service scores failure risk, checks telemetry for anomalies and forecasts stock cover and order completion. An LLM-based layer lets a manager ask operational questions in plain English: the application selects fixed, allow-listed database queries, passes only the retrieved figures to the language model, and rejects any answer whose numbers are not present in that evidence.

The report documents the problem, requirements, design and implementation, and reports measured results only: 438 automated tests pass (269 server, 113 client, 56 ML service), API responses had a median of 3.9 to 7.0 ms on a local machine, and live updates reached a second client in a median of 7.8 ms. The risk model is trained on synthetic data and is not presented as validated on real failures.

Keywords: Industrial Management, Predictive Maintenance, Real-Time Dashboard, Socket.io, MERN, Role-Based Access Control, Machine Learning, LLM-Based Insights, Inventory Control.

Chapter 1: Introduction

1.1 Background

Industrial output depends on four things working together: machines that stay available, workers who are in the right place, production orders that move forward, and materials that are in stock when they are needed. Large manufacturers run enterprise platforms such as SAP, Oracle Manufacturing or Siemens Opcenter to coordinate these. Small and medium enterprises, which make up most of India’s manufacturing sector, rarely can: such platforms need licences, dedicated IT staff and long deployments. Many units therefore continue with paper registers and separate spreadsheets.

The cost of this fragmentation is practical. A stoppage written in a production register is not seen by the stores clerk, who keeps ordering material on the old schedule. A machine can run past its service date because nothing flags it until it breaks mid-shift. A supervisor cannot tell whether today’s target will be met without walking the floor. Each gap is small, but together they push decisions to be late and reactive.

1.2 Introduction to Smart Industrial Management System

The Smart Industrial Management System (SIMS) is a centralised, web-based platform that unifies machine monitoring, worker management, production tracking and inventory control behind one real-time dashboard. Every module shares the same data store and the same event stream, so a change made in one place, for example a machine going offline, immediately updates the alerts, the production bottleneck flags and every connected screen.

SIMS adds an artificial-intelligence layer on top of this operational data. A separate machine-learning service estimates the risk of machine failure, detects unusual sensor readings and forecasts stock and order progress, while an LLM-based assistant answers questions such as “which machine had the most downtime this week?” in plain English using figures calculated by the backend.

1.3 Need for the Project

  • Replace paper and spreadsheet records with one source of truth that every role can see in real time.
  • Move maintenance from reactive repair to planned, data-informed action using downtime history, telemetry and risk scores.
  • Keep inventory lean: detect low stock immediately, draft the reorder and keep a person in control of approving it.
  • Give non-technical managers a way to ask questions of the data without building reports by hand.
  • Enforce who may see and change what, with a record of every change, in a way that suits a single factory.

1.4 Aim and Scope

The aim is to design and build a working, tested prototype of a unified industrial management platform covering five modules: Machine Monitoring, Worker Management, Production Tracking, Inventory Management and an Analytics Dashboard, together with a machine-learning service and an LLM-based natural-language insights layer.

The scope is a single-factory, single-tenant web application. Machine status and sensor values are simulated or entered manually because no physical IoT hardware is connected. The failure-risk model is trained on synthetic data to demonstrate the pipeline end to end; it is an additional signal and not a validated predictor of real failures. Native mobile applications, multi-factory scaling and fully autonomous AI decisions are outside the scope.

1.5 Existing System

In the typical small industrial unit the existing system is a combination of handwritten registers, spreadsheets kept by different departments, and messaging apps. Data is updated late and entered more than once, so figures disagree between departments. There is no common alert path, no history of why a machine stopped, no automatic link between consumption and stock, and no single place where management can see key indicators. Enterprise platforms solve these problems but are too costly and heavy to deploy for most small units.

1.6 Proposed System

SIMS proposes a lightweight, modular alternative. It exposes a REST API and a live event channel, stores all records in MongoDB, and presents them through a responsive React interface in light and dark themes. The system writes downtime and stock history automatically as a side effect of normal actions, raises alerts when thresholds are crossed, restricts every action by role, and offers machine-learning and LLM features as optional layers that fail soft: if the ML service or the language model is unavailable, the rest of the application keeps working.

1.7 Importance of Industrial Automation

Industrial automation and Industry 4.0 aim to make production data available, trustworthy and actionable. Real-time visibility shortens the time between a problem occurring and someone acting on it; predictive maintenance reduces unplanned stoppages, which are the most expensive kind because they halt the whole downstream line; and accurate stock control lowers both over-ordering and stock-outs. Delivering these benefits through a web application running on ordinary hardware lowers the barrier for smaller units, which supports the UN Sustainable Development Goals 8 (decent work and economic growth), 9 (industry, innovation and infrastructure) and 12 (responsible consumption and production).

Chapter 2: Problem Statement

2.1 Problem Definition

Industries face significant difficulty in managing their four operational pillars – machines, workers, production and inventory – efficiently. Most small and medium units depend on manual, paper-based or fragmented digital systems that operate in silos, with no single system talking to another. Real-time, unified visibility across the shop floor is therefore almost impossible, which leads to resource wastage, production delays, unplanned machine downtime and poor inventory control.

The problem is to design and build one connected, role-aware platform that records these four areas in a single database, keeps every user’s view current without manual refresh, and adds machine learning and natural-language insight so that decisions become proactive rather than reactive.

2.6 Challenges and Constraints

  • Data realism: no real failure history was available, so the risk model uses synthetic data; a public dataset was used for an external check, and its limits are stated in Chapters 6 and 8.
  • Consistency across modules: the same event, such as a machine stopping, must update logs, alerts, orders and screens together; this is why every module writes through a service layer that emits events after the database write.
  • Trust in AI output: a language model can state invented numbers, so the design never lets it calculate or look up figures, and it verifies every number in its answer against the evidence.
  • Graceful failure: the ML service and the language model are external dependencies, so every AI feature degrades to a clear message instead of failing the application.
  • Time: the work was planned over eleven weeks with a working increment at the end of each phase.

3.2 Feasibility Study of the Project

3.2.1 Technical Feasibility

Every technology needed is mature, documented and runs on an ordinary laptop: Node.js and MongoDB for the application, React for the interface, Socket.io for live updates, and Python with scikit-learn for the ML service. The riskiest parts, real-time propagation and trustworthy AI output, were prototyped early and are covered by tests; both proved feasible.

3.2.2 Economic Feasibility

The stack is open source and there are no licence costs. Development used existing laptops, a local MongoDB instance and free tiers of hosting services. Running the language model has a usage cost, which the design limits by caching results, rate-limiting calls and making the feature optional. The report does not claim zero total cost: deployment, hosting and model usage would carry running costs.

3.2.3 Operational Feasibility

Users only need a web browser. The interface follows common patterns (tables, a kanban board, forms) and role-based navigation shows each person only the pages they may use. Managers can adopt the AI features gradually because the core screens work without them.

3.2.4 Schedule Feasibility

The work was planned as an eleven-week Agile cycle: requirements and design, database and backend, frontend, machine learning, real-time layer, AI integration, then testing and documentation, with a demonstrable increment at the end of each phase. This schedule was adequate for the five core modules plus the AI layer.

3.4.1 How the Technologies Work Together

A user action in the React interface calls the Express API through an Axios client that attaches the access token. The API validates the request, checks the role and calls a service function. The service writes to MongoDB through Mongoose and, only after the write succeeds, emits a Socket.io event; the browser receives the event and tells TanStack Query to refetch the affected data, so every open screen updates without a reload. Scheduled jobs call the same service functions, so a nightly or hourly job triggers the same events as a manual action.

For machine learning, the Node service assembles numeric features from the database and sends them to the FastAPI service, which returns a risk band, a probability and the factors that raised it; the result is stored and an alert policy decides whether to notify. For natural-language questions, the backend chooses fixed database queries, runs them, and sends only the retrieved figures to the language model, then verifies the reply before showing it. The same figures are shown beside the answer so the reader can check them.

Chapter 4: Design and Architecture

4.1 Overall System Architecture

SIMS follows a four-tier design. The client tier is a React single-page application. The application tier is a Node.js and Express server that owns validation, authorisation, business rules and the real-time channel. The data tier is MongoDB, accessed only through Mongoose models. The AI and ML tier consists of a separate Python FastAPI service for the learned models and an external language-model service that is reached only by the intelligence layer of the application tier.

Figure 4.1: Overall system architecture

Request lifecycle

  1. The browser sends a REST request with the access token; security middleware applies headers, CORS, rate limits and input sanitising.
  2. The authentication middleware verifies the token and reads the user’s current role and active flag, so a role change or deactivation takes effect within seconds.
  3. The route validates the body with a Zod schema and checks the role; the handler calls a service function.
  4. The service reads and writes MongoDB, then emits Socket.io events and, where needed, calls the ML service or the intelligence layer.
  5. The reply uses one envelope, { success, data, message, errors }, so the client handles every response the same way.

Design principles

  • Services own side effects. Events, alerts and notifications are produced by services after a successful write, never by route handlers, so REST calls, scheduled jobs and the simulator all behave identically.
  • AI is optional and bounded. The ML service and the language model sit behind timeouts and fall back to a clear message; neither can write to the database on its own.

4.4 Frontend Architecture

The client is organised by function: pages (one per route, loaded on demand so the chart library is downloaded only when a chart page opens), components (shared interface pieces such as the application shell, dialogs, charts and the notification bell), hooks (the live-update hook), store (Zustand stores for the session, theme and toasts) and lib (the API client with silent token refresh, CSV helpers and shared types). Server data is cached by TanStack Query; the live-update hook listens to Socket.io events and invalidates the matching cache keys, which is how a change on one machine reaches every open screen. Navigation is built from the signed-in role, and routes meant for staff redirect workers to their own page.

4.5 Backend Architecture

The server is arranged as routes → services → models inside one folder per module. Routes only validate, authorise and delegate; services hold the business rules and are the only code that emits events; models define schemas and indexes. Cross-cutting concerns live in middleware: authentication with a short cache of each user’s role, role guards, validation, rate limiting, audit logging and one error handler that turns every failure into the common response envelope. Four scheduled jobs run inside the process: hourly risk scoring, a daily check that opens preventive work orders, a ten-minute escalation of unacknowledged critical alerts, and a weekly summary.

4.10 AI/ML Architecture

The intelligence of SIMS has two paths that share the same database but are otherwise independent: an LLM-based path for natural-language insight and a machine-learning path for numeric prediction.

Figure 4.8: AI/ML workflow – query path and machine-learning path

LLM-based intelligence layer

  1. The manager types a question and chooses a period; the request is validated, role-checked and rate-limited.
  2. A query planner chooses up to three tools from a fixed allow-list (machine status, downtime, production, inventory, attendance, saved assessments, work orders, reliability, stock and order forecasts). It cannot name a collection or write a query.
  3. Each tool runs a fixed database query and returns bounded, already-calculated key figures.
  4. Only those figures are sent to the language model, which writes a short answer. Text from the database is treated as data, never as instructions.
  5. Every number in the answer must appear in the evidence. If not, the call is retried once, and then only the figures are shown.

Machine-learning service

  • Risk model: logistic regression chosen by cross-validation over a calibrated random forest; six inputs (run hours, days since service, downtime events, tool wear, temperature, vibration); trained on synthetic data and labelled as such everywhere it is shown.
  • Sensor model: gradient boosting trained on the public AI4I 2020 dataset using rpm, torque (derived from power) and tool wear.
  • Anomaly and forecast: an Isolation Forest with a robust z-score learns each machine’s own recent telemetry; a trend model forecasts daily stock use and order output with an early and a late estimate.

Chapter 5: Implementation

5.1 Implementation Overview

SIMS is implemented as three programs that run side by side: the API server (Node.js with Express, Mongoose and Socket.io, default port 5000), the web client (React with TypeScript, built with Vite) and the ML service (Python with FastAPI). They are started independently; the client talks to the API through a development proxy or a configured API address, and the API talks to the ML service over HTTP with a timeout. The seed script fills a development database with ten machines, four workers, eight inventory items and a few orders so that every screen has data on first run, and refuses to run against a non-local database unless explicitly confirmed.

The server code is split into one folder per module (access, machines, workers, attendance, production, inventory, alerts, analytics, maintenance, purchasing, telemetry, leave, notifications, planning, insights, simulator, AI and ML). A simulator, available to administrators, advances machine status, readings and order output on a timer through the same service functions used by real requests; it was used to generate the data seen in the screenshots in this chapter.

5.2 Authentication and Role-Based Access

Sign-in verifies the password hash with bcrypt and returns a 15-minute access token (JWT) in the response body and a seven-day refresh token in an httpOnly cookie; the refresh token is rotated on every use and only its hash is stored. On every request the middleware verifies the token and then looks up the user’s current role and active flag (cached for a few seconds), so deactivating an account or changing a role takes effect immediately and a token issued before a password reset is refused. The authorize guard is added to each route that is restricted, and the same check runs when a Socket.io connection is made.

Figure 5.1: JWT authentication middleware and role guard (server/src/middleware/auth.js)

Workers receive further, data-level restrictions inside the services: for example a worker can list only the work orders and orders connected to their own tasks, and can change only the status of tasks assigned to them. These rules are covered by tests that sign in as each role and assert the status code for each protected route.

Testing was done at three levels. Unit tests cover pure rules such as the state machine, the health score, the feature builder, grounding and forecasts. Integration tests start the real Express application against an in-memory MongoDB and call the REST API with each role, so validation, authorisation, side effects and the response envelope are tested together. Chapter 7: Conclusion and Summary

7.1 Summary of Work

This project designed and built SIMS, a centralised web platform that brings machines, workers, production and inventory into one system with live updates. The application tier exposes 132 documented API operations over 26 MongoDB collections; the client has role-specific pages for administrators, managers and workers; and a separate ML service and an LLM-based intelligence layer add prediction and natural-language insight. The code base holds about 5,900 lines on the server, 5,900 in the client and 800 in the ML service, tested by 438 automated tests.

7.2 Objectives Achieved

  • A single dashboard with live machine status, KPIs and alerts that update without a page refresh.
  • Machine monitoring with downtime logging, telemetry, health score, maintenance scheduling and reliability measures (MTBF and MTTR).
  • Worker management with shifts, attendance, leave, tasks and handover notes, and a personal page for each worker.
  • Production tracking with a controlled order life cycle, bill of materials, quality checks and an order feasibility check.
  • Inventory control with atomic transactions, reorder alerts, valuation, suppliers and purchase orders.
  • AI-powered operational insights whose figures are checked against the evidence, with machine-learning predictions that always state their data and limits.

Chapter 8: Limitations and Future Scope

8.1 Limitations

  • Synthetic risk-model data. The failure-risk model is trained on generated data. Its accuracy on real machines is unknown until labelled history from a plant is available.
  • No real sensors. Telemetry is produced by a simulator or entered through the API; there is no connection to PLCs or industrial protocols such as OPC UA or MQTT.
  • Not deployed or load-tested. The system has been run only in development. A deployment description exists, but no hosted instance, concurrency or long-run test was performed.
  • Single plant, single language. There is no multi-tenant or multi-site support, and the interface is in English only.
  • No production rates. Orders carry quantities and due dates but not cycle times, so the feasibility check cannot promise a delivery date.
  • AI service limits. The language-model features depend on an external service; under rate limits or outages the interface shows that insight is unavailable rather than a guess.

8.2 Privacy and Ethical Considerations

The intelligence layer receives only figures that the application has already calculated; names, passwords, tokens and raw records are not sent to the language model. Predictions are always shown as estimates with their data source, and no model can approve a purchase, change a status or edit a record. Decisions therefore remain with the people who use the system.

8.3 Future Scope

  • Connect machines through MQTT or OPC UA gateways and retrain the risk model on real labelled failures.
  • Add mobile applications or a progressive web app with push notifications for supervisors.
  • Add shift-wise production planning, energy monitoring and quality charts (SPC).
  • Add multi-plant support, per-plant roles and scheduled report e-mails.
  • Containerise the three programs and add monitoring, backups and a continuous-integration pipeline for hosted deployment.
